# 2026-08-20 — the operator's documentation report, and what its update pass then showed

Two entries from one operator report, traced to two clauses. A project's `002` step wrote
`.claude/docs/guard-record.md` to 837 lines over five commits and put it in
front of the operator as the step's deliverable; the operator cut it to 237
by hand, losing nothing, and added a budget line to its header that no
doctrine had asked for.

Both halves were prescribed. The record was written as a proof because the
plan made reading it the manual test, and it accumulated rationale and
restatements of rule 9 because nothing said a memory file may not carry
them: rule 3 introduced `.claude/docs/` with a placement clause and no
statement of what the directory is *for*, so `CLAUDE.md` had an economy and
the tier below it had none. The memory-compaction agent's sweep asked three
questions — reachable, consumed, still true — all of them about the file;
the 837-line record was reachable, unconsumed and true, and passed
untouched.

No length rule and no format rule is banked here. Both were considered and
rejected by the operator: the directory's problem was content with no reason
to exist, and a budget the writer sets to fit what they wrote constrains
nothing — the same run's `CLAUDE.md` derived a budget of 390 under U-047 and
sits at 389.

U-065 has a different origin: it was found by watching that same project's
phase-8 pass apply U-063. The pass was clean and its rulings hold — what it
exposed is a rule that U-047 asserted in a changelog remedy and never got
carried into the doctrine text a project restates.

## U-063 — `.claude/docs/` is memory with a job, and no gate rests on reading one

- **Applies to:** running
- **Change:** three connected additions.

  *Rule 3 states what the directory is.* A `.claude/docs/` file is a
  conditional segment of `CLAUDE.md` — loaded at its trigger instead of on
  every run, held to the same test: what a future session needs in order to
  act and cannot get faster from a rule, a docstring or a command it can
  run. Two disqualifiers are named. **Justification** — why a decision was
  taken is `DECISIONS.md`, why a rule exists is the rule. **Duplication** —
  a second copy of what `CLAUDE.md`, the specification, the plan or a
  docstring already says goes stale in silence, because nothing checks it
  against its original. And it is not written for the operator: it is the
  implementer's memory, not a report.

  *Rule 2 states what a gate may rest on.* The operator tests the system's
  behaviour, never a document. A file appears in the manual test
  instructions only when the file *is* the deliverable — an operator
  document, a contract, something under `docs/` — never when it is memory.
  Where a step's real product is a measurement, the test is re-running the
  measurement.

  *The two reviewers of that directory gain the content question.* The
  `optimize-memory` sweep gets a fourth question — does each block earn its
  place — because the three it had judge the file and a file passes all
  three while most of it should go; what it produces is a live file made
  smaller, not a consumed one deleted. And `step-reviewer`'s excess lens
  names memory written as a report rather than as instructions to a future
  session, since it is the only lens that runs on every step and the
  milestone sweep arrives long after the operator has been handed the file.
- **Detect:** a `.claude/docs/` file carrying rationale, a restatement of a
  `CLAUDE.md` rule, of the specification, or of a docstring, or anything a
  session could obtain by running a command; a plan step whose "how the
  operator tests it" is reading a memory file; a `CLAUDE.md` restatement of
  rule 3 that places `.claude/docs/` without saying what belongs in it; an
  instantiated `optimize-memory` whose sweep has three questions.
- **Remedy:** amend `CLAUDE.md`'s rules 2 and 3 and the two instantiated
  assets; then run the sweep with its fourth question over the existing
  directory. Where a plan step still pending names a memory file as its
  test, rewrite the test as an observation of the mechanism — a plan
  amendment, logged.

## U-064 — the probe record carries its three fields and nothing else

- **Applies to:** bootstrap
- **Change:** step `001`'s measurement prescription keeps its three fields
  — the version measured on, the method, the re-measure recipe — and gains
  its boundary: why a probe was worth running, what rule 9 gates and what
  the guard's own docstring explains each already have a home, and a
  restatement in the record is the duplication U-063 disqualifies. The
  operator's test of the step is the liveness triple, not the record.

  Reasoning: the field list read as a floor with no ceiling, in a step whose
  output the plan was simultaneously calling a deliverable. Measured: fifteen
  probes written as four prose fields each, plus 300 lines re-explaining the
  permission boundary a second time, then a hand cut to a third of the size
  that lost nothing the record was for.
- **Detect / Remedy:** bootstrap-time; a project past `001` is reached by
  U-063's remedy instead.

## U-065 — the headroom belongs to the budget number, not to the baseline

- **Applies to:** running
- **Change:** rule 3's headroom requirement is attached to the budget
  itself, however it is arrived at — the baseline, one derived at the first
  task under U-047, or one re-derived later because a doctrine change added
  lines. Every one of them lands with room left against itself, and a budget
  re-derived to exactly the length of the file that prompted the
  re-derivation has recorded that file rather than budgeted it.

  Reasoning: U-047's **remedy** already said "keep the headroom rule against
  the derived number" — and that sentence lives only in the changelog, which
  no project reads. Rule 3, which is what a project restates into its own
  `CLAUDE.md`, attaches headroom to the two illustrative numbers ("around
  180, not 219") and says nothing about a number the project derives for
  itself. So the requirement has never reached a running project.

  Measured in the project that produced U-063: its first derivation landed
  at 389 against a 390 cap, and its re-derivation under U-063 landed at 400
  against a 400 cap — twice, the number was set to the length of what had
  already been written. The second entry states plainly that the next step
  arrives needing a compaction pass it did not budget for, which is the cost
  this rule exists to move one decision earlier. Both were logged decisions
  with alternatives weighed, so neither is a deviation to correct on sight;
  what they show is a rule that was never carried where it binds.
- **Detect:** a project whose `CLAUDE.md` sits at or within a line or two of
  the budget its own rule 3 states; or a decision entry re-deriving the
  budget whose new number equals the file's current length.
- **Remedy:** at the next re-derivation, set the number above the file's
  obligations rather than at them, and take the compaction the previous
  derivation deferred. A file already at its cap is not re-cut for this
  alone — the rule binds on the next change that touches the budget.
