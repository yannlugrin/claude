# 2026-08-19 — one handoff's own review rounds, banked at source

Both entries come from one project's phase-7 run: eight review rounds on a
single bootstrap prompt, five of them on the session's own model and three
divergent, recorded in that project's `upstream-findings.md` as they were
found. They are the first entries produced by the upstream-findings channel
running end to end — found in a project, recorded there, applied here.

The run also produced four reusable patterns and three new doctrine
questions that are **not** banked here; they remain in that project's
findings file awaiting a ruling, and the next revision is where they land
if they are taken.

One repair carries no id: five templates had a swallowed line break inside
their instantiation header (`… any of them.>`), introduced when the U-051
and U-053 blocks were inserted. The header is deleted at instantiation, so
nothing reaches a project and no project needs to detect anything — fixed
at source and noted here only so the next reader does not go looking for
the entry.

## U-057 — the handoff prompt's fourteen review-round fixes

- **Applies to:** bootstrap
- **Change:** fourteen corrections to the prompt template's fixed text,
  each found by a review round on a real handoff and none of them
  project-specific. Grouped by what they repair:

  *Claims the template made that it forbids elsewhere.* Step `001`
  declared "this prompt names no modes and asserts no mode behavior" and
  then, two sentences later, asserted a mode taxonomy and an
  auto-accept-edits consequence — both are now tagged as illustrations to
  re-derive from the running version, which is what U-022 asked of every
  other carrier. Step `003` asserted that a fresh-setup proof "may ride a
  scheduled job the specification already requires", inventing a
  requirement for the majority of specifications that have none, and
  setting the first task's two reviewers up to contradict each other; the
  clause is now conditional on the specification actually carrying one.

  *Rules that collided or dead-ended.* Rule 9's enumeration never
  acknowledged rule 6's step-close push exception, so a faithful
  whole-carry into `CLAUDE.md` — which rule 9 demands — produced two rules
  contradicting each other; the exception is now named inside rule 9,
  with the reason it has to be. Rule 6's push attempt had no no-remote
  branch, so the closes of `000` and `001` attempted a push at nothing,
  the two closes that happen before `approve-step` exists to handle it.
  Rule 3's eviction order named its third tier "per-track detail that the
  track's own plan already carries" — unreadable in a single-track
  project, which is most of them, and unreadable exactly when the budget
  binds; it is now phrased for both shapes.

  *Prescriptions with no reviewer.* The fidelity subagent read "only this
  prompt's foundation-step prescriptions and the plan", which left the
  two `CLAUDE.md` restatement failure modes the template itself
  documents — a dropped clause, and a sentence citing a clause the file
  no longer contains — checked by nobody: the cold reviewer is
  structurally barred from the prompt, and this subagent was scoped away
  from `CLAUDE.md`. It now reads the prompt in full plus the plan,
  `CLAUDE.md` and `README.md`. The foundation-transcription list said
  "the permission classifier and its traps", which names nothing a
  checklist can be run against; its intended contents are now
  enumerated. The step-`002` test ("I invoke each ritual and see it do
  what it claims") is unsatisfiable for the agents whose only trigger is
  a milestone close, and misattributed the close ritual, whose first
  real trigger is step `002`'s own close; real invocations and smoke
  tests are now split, with the deferred proof stated.

  *Coverage the slot guidance omitted.* `{{STATIC_CHECKS}}` never
  mentioned YAML, although the doctrine's own default stack lands a
  hook-runner configuration at step `000` — the first artifact of any
  class the repository gets, and the one family guaranteed to exist from
  step one was the one the expected instance left out. The guard's
  "width exemption" is two exemptions: a lint width **and** a formatter
  exclusion, with the `force-exclude` wrinkle where the runner passes
  filenames explicitly — stated as one, the first format run reflows the
  vendored file. The unfillable-placeholder carve-out named a single
  instance (the state reviewer's architecture vocabulary) and therefore
  read as that one file's exemption, while `resume-step`'s world-state
  checks are the same case; it is now a general rule with two standing
  examples.

  *Two gaps in the foundation steps.* Step `001`'s baseline never
  protected its own files, though the whole pairing depends on the
  settings staying intact: under a mode that auto-accepts file edits,
  one silent, well-formed settings edit that drops the push gate turns
  the close ritual's standing push attempt into an unprompted publish,
  and the governance checks catch malformation but never a well-formed
  loosening. Ask-tier file rules on the settings file and the hooks
  directory now land inside that same proposal. And step `003`'s first
  push published `.claude/spec-work/` — the specification phase's whole
  history, its review reports and any template still sitting there —
  with nobody asked; publish-or-strip is now an explicit logged decision
  of the forge step, made before the push it becomes irreversible at.
- **Detect:** bootstrap-time only. A project handed over before this date
  may show any of them individually; the two worth checking, because
  nothing else would surface them, are whether its `CLAUDE.md` restates
  rule 9 without rule 6's push exception (two contradicting rules, and no
  reviewer ever looked), and whether `.claude/spec-work/` went public at
  the first push without a decision entry.
- **Remedy:** none automatic. For the rule 9 / rule 6 collision, one
  clause in `CLAUDE.md` under the project's own conventions. For a
  repository already public, the decision is made rather than
  reconstructed: ask the user now, and strip or keep with an entry
  either way.

## U-058 — three template defects a real handoff's review rounds found

- **Applies to:** running
- **Change:** three corrections to the tooling templates, each found by a
  review round on a real handoff:

  **`bash_guard.py`'s pairing doctrine said "for every tool in the
  registry, add a broad allow"**, and its `REGISTRY` banner repeated it
  as "pair every tool here with a broad allow". Both read as mandating a
  broad allow on the `SHELL_WRAPPERS` layer — a `Bash(sudo:*)`-class
  line — which is the exact command-runner hole the same docstring
  forbids elsewhere: a broad allow on a command-runner is a broad allow
  on everything it runs the moment the guard is dead. Both are rescoped
  to rule- or grant-bearing tools, with the wrapper layer named as the
  exclusion rather than left to be inferred.

  **`approve-step` ran the milestone passes before the push**, and
  `optimize-memory` never commits by design, so every milestone close
  pushed the close commit and its tag while the reviewed compaction sat
  uncommitted in the tree — unpublished until the next close, in a
  ritual that never mentioned it. Step 5 now lands the reviewed
  compaction as a `meta:` commit before the push, or discards it out
  loud.

  **`handover-step`'s header listed `{{CHECK_COMMAND}}` and
  `{{TEST_COMMAND}}`** among its placeholders while its body uses only
  `{{VERIFY_COMMAND}}` and `{{STEP_ID}}`, sending the instantiating
  session hunting for two referents the file never needs. Header trimmed
  to what the body contains.
- **Detect:** the project's `.claude/settings.json` carries a broad
  `Bash(<wrapper>:*)` allow for a name in the guard's `SHELL_WRAPPERS`
  layer (`sudo`, `env`, `xargs` and their neighbours); or its
  instantiated `approve-step` runs the milestone passes with no commit
  step before the push; or its instantiated `handover-step` header names
  placeholders its body does not use.
- **Remedy:** the wrapper allow is a permission-baseline change and goes
  to the user for review — dropping it is the fix, and the guard's
  wrapper entries keep seeing through the wrapper either way. The other
  two are edits to the instantiated files under the project's own
  conventions, in a `meta:` commit.
