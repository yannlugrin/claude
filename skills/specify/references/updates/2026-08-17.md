# 2026-08-17 — handoff findings from one project's third handoff iteration, another project's specification-run review, and the operator's review of the first project's bootstrap output

Entries U-022 to U-033 come from one project's handoff: the first five
from that project's `upstream-findings.md` and from a review of the phase
itself, the rest process changes to this skill.

Entries U-034 to U-041 come from a review of a completed specification run
(twenty review rounds, two challenges, two external
reviews, an operator reading pass, 2023 lines). They are process findings
about phases 4 to 6 — where the yield is, where the sequence stops, and what
counter-pressure the phase has against its own output. That run had no
carrier for such findings, which is itself the first of them; they were
reconstructed after the fact from git history and the review archive.

Entries U-042 to U-047 come from the operator's own review of what one
project's bootstrap produced — the plans, logs, `CLAUDE.md` and README a
handed-over session wrote before its first step — after they challenged one
of its structural choices. They are the first findings gathered from a
bootstrap's *output* rather than from the phase that generated it, and five
of the six concern the same blind spot: what the repository ships, versus
what its documents happen to describe.

## U-022 — permission-mode names are read from the harness, never asserted

- **Applies to:** running
- **Change:** neither the handoff prompt nor `bash_guard.py`'s docstring
  names permission modes or asserts their behavior. Both now say that the
  mode set, and what each mode does to a command no rule matches — prompt,
  auto-approve, or hand it to a classifier that may itself refuse — are
  properties of the installed version, taken from it and probed at the step
  that sets the baseline. The classifier case is a real third answer to
  what backs the guard's silence, and no earlier wording had it. Reasoning:
  the names change between versions, and *both* attempts to fix the
  vocabulary in place were wrong within one release — the first named a
  mode that had been renamed, the correction denied a mode that exists and
  named one the flag no longer accepts. A version-stamped fact restated in
  standing instructions outlives its version in silence, which is the
  failure the prompt's own probe discipline exists to prevent.
- **Detect:** the project's `CLAUDE.md`, its permission-baseline
  `.claude/docs/` file, or its instantiated `.claude/hooks/bash_guard.py`
  docstring names a specific permission mode as a standing fact (`auto`,
  `default`, `dontAsk`…) without a measured-on-version stamp beside it.
- **Remedy:** reword to the behavioral classification; keep named modes
  only in the probe record, each with the version it was measured on. Where
  the project's committed `permissions.defaultMode` is itself a name the
  running version no longer accepts, that is a baseline change and goes to
  the user for review.

## U-023 — the close-ritual track rule needs a carrier past bootstrap

- **Applies to:** running (multi-track projects only)
- **Change:** in a multi-track project, the rule that close rituals key on
  the track of the step *just closed* — never on the `Current state`
  pointer the close has already advanced — must be named in the list of
  what `CLAUDE.md` carries and in the step `002` plan entry, not only in
  the bootstrap prompt. Reasoning: the prompt is consumed once. Stated only
  there, the rule survives exactly where the concise restatement happens to
  keep it, and nothing checks that it did; the failure is silent (a state
  reviewer reading the wrong track's plan reports nothing wrong) and
  arrives at the first cross-track milestone boundary.
- **Detect:** the project has more than one track, and neither `CLAUDE.md`
  nor the plan entry that instantiated the tooling states which track the
  milestone passes receive.
- **Remedy:** add the sentence to `CLAUDE.md`'s governance-placeholder
  paragraph, and to the instantiated `approve-step` — its header and the
  step that spawns the milestone passes both now name the closing track
  explicitly, since step 3 has already advanced the pointer. The template
  side of the same defect is fixed here; a project that instantiated the
  earlier copy carries it.

## U-024 — a named task runner obliges the no-gated-act invariant

- **Applies to:** running
- **Change:** wherever the prompt names a task runner (`just`, `make`,
  `npm run`, `task`), it also states the invariant that no recipe performs
  an act the action boundary gates, and the permission-baseline step
  records it as a rule of the baseline. Reasoning: a `PreToolUse` guard
  judges the command string it is given — it sees `just release`, never the
  `docker push` inside the recipe — and no permission rule reaches inside
  one either, so a gated act behind a recipe name bypasses the gate unseen.
  The obvious alternative, gating the runner itself, prompts on every
  `just check` and destroys the development loop the boundary's free side
  exists to protect.
- **Detect:** the project has a task runner, and its recipes include a
  publish, push, deploy or other act rule 9 gates; or the runner appears in
  the guard registry with no stated treatment either way.
- **Remedy:** move the gated act into CI or into a direct command, state
  the invariant in `CLAUDE.md`'s harness section, and add the guard case
  that keeps it honest.

## U-025 — one step's change is the previous `step-*` tag of any track

- **Applies to:** running (multi-track projects only)
- **Change:** the single-track statement "`git diff` between two tags is
  exactly one step's change" does not survive tracks. With one linear
  history and interleaved tracks, a step's change is the range from the
  previous `step-*` tag of *any* track — the same tag the re-orientation
  routine finds with `git describe --match 'step-*'` — never from that
  track's own previous tag, which sweeps in every other track's steps that
  landed between the two. The compacted plan entry's "previous step tag"
  means that tag as well.
- **Detect:** a multi-track project whose rule 6 (in `CLAUDE.md` or the
  prompt it was bootstrapped from) says "between two of a track's tags", or
  whose compacted plan entries cite a tag range that skips over another
  track's tag.
- **Remedy:** reword rule 6 and the plan-entry convention; existing
  compacted entries are left as they are — history is not rewritten for a
  citation — unless the user wants a sweep.

## U-026 — `.claude/worktrees/` stays ignored across the handoff

- **Applies to:** running
- **Change:** the foundation step that writes `.gitignore` carries
  `.claude/worktrees/` forward, and the prompt says the file is being
  rewritten rather than created — what the specification phase put there
  stays. Reasoning: worktree isolation materializes a reviewer's checkout
  inside the repository, and a commit made while one exists swallows it.
  The specification workspace ignores it from setup; the handoff's ignore
  list did not name it, so the first session to rewrite the file drops it.
- **Detect:** `git check-ignore -q .claude/worktrees/` fails in the project.
- **Remedy:** one line in `.gitignore`, in a `meta:` commit.

## U-027 — the reviewer context block names the expected branch

- **Applies to:** spec phase
- **Change:** the context block's `Expected HEAD` line carries the branch
  name alongside the commit hash, and the prose says why. Reasoning: in a
  repository with several lines of work, an isolated worktree materializes
  at a plausible wrong checkout — a sibling branch's tip reads as a real
  project rather than as an error, and only the commit hash distinguishes
  them. Observed twice in one phase; the existing guard held both times,
  but only because the reviewer checked.
- **Detect:** the context block generated for a review carries a commit
  hash and no branch.
- **Remedy:** template change only; nothing to carry into a project.

## U-028 — the compression pass reports its delta

- **Applies to:** spec phase
- **Change:** phase 7's compression pass reports the line and word delta
  against the prompt as first written, in the commit and to the user.
  Reasoning: measured on one real phase, three review rounds added 81 lines
  and the compression pass removed two — and the commit subject said
  "compression pass". Unmeasured, a nominal pass reads as a done one; the
  pass exists because the prompt must stay restatable into a `CLAUDE.md`
  under its line budget.
- **Detect:** phase-7 process only; not applicable to a running project.
- **Remedy:** none in-project.

## U-029 — `.claude/refs/` is excluded from the check harness

- **Applies to:** running (projects with references only)
- **Change:** where the user supplied reference material under
  `.claude/refs/`, that path joins `.claude/spec-work/` in the check
  harness's standing exclusions. Reasoning: a reference is read-only for
  every session and its authority lives elsewhere, so a lint finding inside
  one has no legal resolution — the file cannot be edited, and the
  bend-the-config escape is written for the specification alone. Two
  reasonable implementations diverge observably: one bends the lint to the
  reference, one logs an exclusion, one leaves the check red.
- **Detect:** the project has `.claude/refs/` populated and its check
  command's file list reaches into it.
- **Remedy:** one path exclusion in the harness configuration, with its
  reason recorded where the other exclusion's is.

## U-030 — the memory-compaction agent carries the action boundary

- **Applies to:** running
- **Change:** `optimize-memory` carries the same action-boundary paragraph
  the reviewer agents carry — everything rule 9 merely *gates* is, for a
  subagent, forbidden outright, since a subagent has no exchange to be
  gated in. Reasoning: it holds the broadest `tools:` of the agent set
  (it writes), and it was the only one whose sole constraint was "you never
  commit". The asymmetry was in the template, not in a project's choices.
- **Detect:** the project's instantiated `.claude/agents/optimize-memory.md`
  has no boundary paragraph, or cites rule 9 without the
  gated-means-forbidden reading.
- **Remedy:** add the paragraph; where the subagent-context probe (U-022's
  neighbour, the `CLAUDE.md`-reaches-subagents probe) failed in this
  project, inline the gated set instead of citing it.

## U-031 — agent templates order a re-probe rather than citing an old result

- **Applies to:** running
- **Change:** `step-reviewer` and `state-reviewer` no longer assert "a probe
  confirmed `CLAUDE.md` reaches every subagent's context" as settled fact.
  The result is attributed to the project that produced the template, a
  re-probe is ordered at instantiation, and the unfavorable branch is
  pre-committed: inline the gated set in the agent body, logged with its
  single-source-of-truth cost, never a citation to a rule the agent cannot
  read. Reasoning: stated as fact, it biases instantiation toward the
  citation form — and if the mechanism does not hold in the version being
  run, the agent cites a boundary that is not in its context and the
  failure announces nothing.
- **Detect:** the project's instantiated reviewer agents cite rule 9 for the
  gated set, and no probe result in `.claude/docs/` records that
  `CLAUDE.md` reaches subagents in the version the project runs.
- **Remedy:** run the probe; keep the citation if it holds, inline the set
  if it does not, and record the measurement with its version.

## U-032 — triage verifies reviewer-asserted environment facts

- **Applies to:** spec phase
- **Change:** standing rule 3 now binds triage as hard as it binds
  drafting: a finding that asserts what a harness, platform or provider
  defines is verified against the real thing before it is applied.
  Reasoning: a reviewer runs on training knowledge like anyone else, but an
  accepted finding arrives with the authority of a review. Measured once —
  a cold round asserted a permission-mode list, the triage applied it
  unverified, and the correction was wrong in a way the original text was
  not (U-022).
- **Detect:** phase 4/7 process; not applicable to a running project.
- **Remedy:** none in-project.

## U-033 — the handoff prompt's ten review-round fixes

- **Applies to:** bootstrap
- **Change:** ten corrections to the prompt template's fixed text, each
  found by a review round on a real handoff and none project-specific: the
  first task's opening matches its own closing sequence and states why it
  is one ungated unit; rule 1 names the winner of its collision with
  rule 6 rather than admitting an unresolved one; the `{{OPEN_FACTS}}`
  latitude says the escalation list wins where both clauses apply; the
  subagent-context probe carries a pre-committed unfavorable branch
  (inline the gated set, logged) like the rules-file probe beside it; that
  probe is scoped to the first agent *step `002`* spawns, never the
  bootstrap cold reviewer; a second, deliberately non-cold subagent checks
  that the foundation plan entries actually carry this prompt's
  prescriptions — the cold reviewer cannot, being barred from the prompt;
  the governance frontmatter check is sanctioned explicitly against
  rule 11; step `000` is scoped to the harness skeleton plus the families
  whose artifacts exist there; and Python is a standing check family for
  the shipped guard, with its width exemption.
- **Detect:** bootstrap-time only. A project handed over before this date
  may show the symptoms individually — its foundation plan entries thinner
  than the prompt that produced them is the one worth checking, since
  nothing else would surface it.
- **Remedy:** none automatic; where the foundation is already built, the
  detail lives in the built repository rather than the plan, and a rewrite
  buys nothing.

## U-034 — the specification phases carry their own upstream-findings file

- **Applies to:** spec phase
- **Change:** phase 6 gains a closing step: write
  `.claude/spec-work/upstream-findings.md` — what the run learned about the
  process rather than the project (a rule that never fired, an improvised
  lens, a step whose cost outran its yield, a deliberate deviation). Phase 7
  names it beside its own file in the closing message, never merging the two.
  Reasoning: phase 7 has had such a file since it was measured that generic
  findings otherwise die in the session that produced them — and phases 1–6,
  which are most of the process, had none. Measured: a twenty-round run's
  process findings existed nowhere and had to be reconstructed from git
  history and the review archive by a later session that happened to look.
- **Detect:** spec-phase process; a finished run whose `.claude/spec-work/`
  holds reviews and a decision log but no `upstream-findings.md`.
- **Remedy:** none in-project; for a run already finished, the file can still
  be written from the review archive, which is what produced these entries.

## U-035 — "quiet" means no requirement-changing finding, not an empty round

- **Applies to:** spec phase
- **Change:** a phase-4 round is quiet when the user accepts no
  *requirement-changing* finding — a new must, a changed tier, a decision
  moved. Clarifications, restatements and editorial repairs no longer reset
  the count. Reasoning: read as "nothing substantive accepted", the criterion
  is unreachable on a mature document. Measured over twenty rounds: not one
  came back empty, every archived verdict read *not quiet*, and the sequence
  ended when the operator decided it had had enough — a good reason to stop
  that the written rule could not express, leaving the process with a
  criterion it never met and a stop nobody recorded.
- **Detect:** a review archive whose every verdict line says "not quiet",
  with no round-count or stopping rule recorded anywhere.
- **Remedy:** none in-project.

## U-036 — triage weighs cost, and every round reports the line delta

- **Applies to:** spec phase
- **Change:** phase-4 triage states what a finding costs the document as well
  as what it buys, and the triage commit reports the specification's line
  delta. Reasoning: two measurements from one run. About a hundred and ten of
  a hundred and eleven labelled findings were applied — while reviewer
  *questions* in the same reports were regularly answered without change, so
  the label, not the argument, was doing the arbitrating. And the document
  went from 1270 to 2023 lines across twelve rounds with not one commit ever
  reducing it: the phase has no subtractive force at all, and the compression
  pass at the far end cannot recover what twelve rounds added.
- **Detect:** spec-phase process; a review archive where the triage record
  shows every finding accepted, or triage commits carrying no size figure.
- **Remedy:** none in-project.

## U-037 — a neutralized-benefits diagnosis owes a subtractive proposal

- **Applies to:** spec phase
- **Change:** where a challenge names the neutralized-benefits pattern,
  reaffirmation is an answer only with a retirement condition or a concrete
  simplification attached for the user to rule on; `challenger.md` states it
  in the report structure and phase 5 holds the triage to it. Reasoning:
  measured, a challenge diagnosed the pattern as "textbook shape" on a
  mechanism carrying seven accumulated hedges and a defaults layer serving
  its one remaining use, recommended reaffirmation with directions, and the
  mechanism reached the final audit whole. The instrument built to catch
  accretion named it and changed nothing — because "reaffirm or reopen"
  offers no move between keeping a thing as it stands and reopening the
  decision behind it.
- **Detect:** a challenge report naming the pattern whose recommendation is a
  bare reaffirmation.
- **Remedy:** none in-project.

## U-038 — the finalization compression pass reports its delta too

- **Applies to:** spec phase
- **Change:** phase 6's compression pass reports its line and word delta in
  the commit and to the user, as U-028 already requires of phase 7's.
  Reasoning: the asymmetry had no justification, and the unmeasured side
  failed the same way. Measured: the pass changed not one line, argued its
  restraint in the decision log — plausibly correctly — and the commit said
  "compression pass". Where restraint is the answer the numbers are the
  argument for it, not a substitute for one.
- **Detect:** spec-phase process; a run whose compression commit carries no
  figures.
- **Remedy:** none in-project.

## U-039 — "strongest available" names its candidates

- **Applies to:** spec phase
- **Change:** a spawn proposal claiming the strongest available model names
  what it compared against. Reasoning: unexamined, that claim's answer is
  always the model already running. Measured: one run put both challenges and
  the final audit on the session's own model, each header asserting "strongest
  available", with a divergent strong model in use elsewhere in the same run
  — where it returned eighteen and fifteen findings against a five-to-eight
  baseline from its same-model neighbours. Sixteen of twenty rounds went to
  the session's model; the divergence remains the highest-yield lever measured
  anywhere in this process.
- **Detect:** archived review headers claiming "strongest available" with no
  named comparison, on a project where another strong model was spawned.
- **Remedy:** none in-project.

## U-040 — two lenses, and a protocol for the operator's reading pass

- **Applies to:** spec phase
- **Change:** `reviewer.md` gains a **focused artifact audit** lens (a
  companion artifact judged against its own bar, re-derived rather than
  trusted, with a spec-conflict inventory) and a **source comparison** lens (a
  specification serializing a prototype, judged for what the retelling lost).
  Phase 6 gains the protocol for an operator reading pass: opinion per
  comment, ruling recorded, nothing edited until the user declares the pass
  finished, then one batch. Reasoning: all three were improvised on one run
  because nothing standard fitted, and all three earned their keep — the
  artifact audit re-derived a 316-ruling corpus independently and found three
  context omissions before an irreversible deletion; the comparison lens found
  a rule whose direction the specification had *inverted*; the batch protocol
  exists because editing while the operator reads moves the text under a
  reader who is still in it.
- **Detect:** spec-phase process only.
- **Remedy:** none in-project.

## U-041 — review worktrees are pruned when the phase ends

- **Applies to:** spec phase
- **Change:** the workspace rule now says that ignoring `.claude/worktrees/`
  is not disposing of it: prune the checkouts when the phase ends, before the
  handoff and its squash. Reasoning: measured at the end of one run — sixteen
  checkouts, eight megabytes, still registered against the repository's former
  path after a rename, and still holding copies of the `.claude/refs/`
  material that a commit had deliberately removed from the tree so the
  implementer would never receive it. Ignored files survive both the removal
  and the squash, and a bootstrap session listing the repository finds them.
- **Detect:** `git worktree list` shows prunable entries, or
  `.claude/worktrees/` exists at handoff time.
- **Remedy:** `git worktree prune`, then remove the directory.

## U-042 — tracks are enumerated from deliverables, not from documents

- **Applies to:** running (multi-track projects)
- **Change:** the monorepo section of `handoff.md` now says the track list
  comes from what the repository ships, never from the per-component
  documents that happen to exist, and that a component specified directly by
  the root document gets the pointer `SPECIFICATIONS.md` `structure.md`
  already mandates — raised as a finding against the specification under rule
  1, before the plans are written. `structure.md` gains the matching rule at
  its own end: the section defining the per-component document names the
  class by deliverable, and the finalization sweep checks that name against
  the full deliverable list. Reasoning: measured on a repository of game
  images plus the builder image they all build from. The root document titled
  its section "Per-game specifications", so the builder — an image peer in
  every other section, with its own tags, its own publish gate and its own
  GHCR page — fell outside the class, got no document, and therefore no
  directory and no owner. The handoff then derived its tracks from the
  documents and could not see the omission; nothing downstream could either.
- **Detect:** a shipped deliverable that has no `SPECIFICATIONS.md` of its
  own and no track — most visibly, one whose files have no stated directory.
  Equivalently: the plans' deliverables do not account for every image,
  service or package the specification says the repository publishes.
- **Remedy:** amend the root document so the class covers the deliverable
  (user's approval, rule 1's channel: entry before amendment, one commit),
  create the component directory with its pointer specification, plan and
  log, register the track, and move the steps. Free while every affected step
  is `pending`; after the first tag on them, the numbers are frozen and the
  move costs more.

## U-043 — ownership follows artifacts, not blast radius

- **Applies to:** running (multi-track projects)
- **Change:** the monorepo section states the assignment rule outright — the
  question is where a deliverable's files live, not how far its changes
  ripple — and declares the root track's charter **closed** (foundation and
  harness, CI, shared documentation, root-level files). Widening it to hold a
  shippable component is a logged decision with a reason. It also names the
  visible-on-sight tell: a milestone in the root plan named after a single
  deliverable is a track wearing a disguise. Reasoning: asked to defend a
  component sitting on the root track, a session produced "its work ripples
  repository-wide" — true, and the wrong test: every dependent's changes
  ripple, which is what cross-track dependency edges exist for, whereas CI is
  root-owned because `.github/workflows/` is a root directory. Unstated, the
  criterion is chosen by whichever reading the session reaches for first, and
  "ripples widely" reads as the responsible one.
- **Detect:** the root track owns a deliverable that is neither a root-level
  nor a shared artifact; or a root-plan milestone is named after one
  component.
- **Remedy:** move it to its own track, or record the reason it is
  root-owned in the track-map decision (U-044). Publication workflows stay
  root-owned even when they publish a component's artifact — that is the
  charter applied, not an exception to it.

## U-044 — the track map is a logged decision, not an inherited line

- **Applies to:** running (multi-track projects)
- **Change:** the first task's `DECISIONS.md` gains a second entry beside
  "adopt this workflow" — the track map, with every component considered and
  every root-owned deliverable named with its reason. The prompt's map is
  explicitly a *proposal* the implementer re-derives and logs, agreement
  included. Reasoning: measured. A bootstrap prompt added a shippable image
  to the root track's charter in one clause; the implementing session
  transcribed it into the track map and logged only the workflow adoption.
  Challenged later, that session's own diagnosis was "I inherited it rather
  than deciding it… the reasoning is nowhere, which is why you can ask this
  question and find no answer in the repository". The defence it then
  constructed was sound work done at the wrong time — the moment to make that
  argument was the first task, when moving a step was still free.
- **Detect:** the track map exists in `CLAUDE.md` with no decision entry of
  its own; or the log's workflow-adoption entry carries the track assignment
  as a sub-clause.
- **Remedy:** write the entry now, against the current map — re-deriving it
  under U-042 and U-043 first, since the entry has to state a conclusion
  rather than a transcription.

## U-045 — deliverables state where their files land, and the cold review checks it

- **Applies to:** running
- **Change:** the plan's per-step shape now requires deliverables to name
  their location wherever the specification does not already fix it (the
  directory once per deliverable; the files inside need no enumeration), and
  the bootstrap cold review gains a **layout and ownership** lens: every
  deliverable has a stated location, nothing shipped is left without one,
  and — where there are tracks — every deliverable has an owning track.
  Reasoning: the existing lenses cannot see this failure. A component with no
  directory passes coverage (its sections are mapped to steps), ordering,
  granularity, prerequisites and consistency untouched; it surfaces only when
  someone builds it. Observed: a plan step read "a Dockerfile" with no path,
  in a repository whose only other image lived in a named directory — the
  next session would have put it at the root beside the task runner, making
  the contributor guide describe two shapes.
- **Detect:** a step whose deliverables create files but name no directory,
  where the track's own directory does not settle it; or a `README.md` file
  map whose growth list omits an artifact the plan builds.
- **Remedy:** state the directory in the step's deliverables and in the file
  map, in the same pass.

## U-046 — the per-component class is checked against the deliverable list

- **Applies to:** spec phase
- **Change:** phase 6's final consistency sweep gains the component-class
  check: where the specification is split, every shipped deliverable is
  inside the class the root document names, or has a written reason for being
  outside it. Reasoning: the same measurement as U-042, seen from the phase
  that could have prevented it. Naming the class after the interesting
  majority (*per-game*, *per-service*, *per-plugin*) reads as complete while
  excluding the shared or foundational deliverable everything else builds on
  — and that exclusion is invisible from every later phase, because they all
  enumerate components from the documents the split produced.
- **Detect:** the root section defining per-component documents is named
  after a subset of what the repository ships.
- **Remedy:** widen the class name, or state the excluded deliverable's
  reason in the same section. Either is a specification change and goes to
  the user.

## U-047 — the `CLAUDE.md` budget is derived when its floor is already visible

- **Applies to:** running
- **Change:** rule 3's line budget says its numbers are a **single-track
  baseline**, and that a project which can already see a higher floor at the
  first task — a long boundary enumeration, many source-of-truth directories,
  a track map — derives its own budget then and logs it, rather than landing
  over the cap and deviating afterwards. The discipline is unchanged and is
  what actually binds: headroom, the eviction order, rule 9's enumeration
  never leaving. Reasoning: a multi-track project landed at 254 lines against
  a 220 cap and logged a deviation raising it to 280 with a ~250 target — the
  arithmetic in that entry is convincing (rule 9 carried whole is 35 lines,
  the required sections ~90), which is the point: the number was
  unreachable from the start, and a budget first met by breaching it teaches
  the next session that the budget is decorative.
- **Detect:** the project's `CLAUDE.md` exceeds the budget its own rule 3
  states, with no logged deviation; or a deviation entry that raises the
  budget at the first close rather than at the first task.
- **Remedy:** derive the budget from the file's actual obligations, log it,
  and keep the headroom rule against the derived number.

## U-048 — a step moved into a track carries its ordering as an edge

- **Applies to:** running (multi-track projects)
- **Change:** the monorepo section's rule 6 adaptation now says that what a
  step's position used to guarantee, a dependency edge must state — and names
  the first one: every component track's first step depends on the
  foundation's last step. Reasoning: measured immediately after a project
  moved two steps out of its root plan into a new component track. The move
  was otherwise exemplary — references swept, coverage remapped, cross-track
  edges symmetric, verified by a fresh-context subagent — and the component
  track's first step ended up depending on the harness skeleton alone,
  because that was the only dependency worth writing down while its position
  in the root plan said the rest. By the plans' own sequencing rule the
  builder and every downstream track were then startable before the
  permission baseline, the reviewer agents, the rituals and CI existed. The
  failure is quiet: the plans stay internally consistent, every reference
  resolves, and nothing reports it.
- **Detect:** follow each component track's first step through its
  `Depends on` chain; if it reaches the foundation's last step, it is
  ordered. A chain that terminates at the harness step — or anywhere inside
  the foundation — leaves the track startable mid-foundation.
- **Remedy:** one clause in the dependency line of each component track's
  first step; the rest of that track inherits it. Free at any time, since it
  changes no step number.

## U-049 — an agent verifies its own premise instead of inheriting a probe

## U-050 — the compaction agent reads the line budget, never restates it

## U-051 — a governance placeholder in a multi-track repository is a table

## U-052 — `tools:` binds which tools exist, not what they can do

- **Applies to:** running
- **Change:** every agent template header, and the shared-conventions
  paragraph in `handoff.md`, now carry the limit beside the binding claim: an
  agent listing `Bash` can write files whatever else its `tools:` line omits,
  so a reviewer's read-only discipline rests on the prose in its body and not
  on its frontmatter. Only `tools: Read` alone makes writing mechanically
  impossible — and an agent reduced to it needs another route to whatever
  `Bash` was fetching, a diff above all. Reasoning: the previous wording
  ("`tools:` binds, and an unlisted tool is absent rather than refused") is
  true and invites the wrong conclusion, because a list that visibly omits
  `Write` and `Edit` reads as a sandbox. Measured live: an agent declaring
  `Read, Bash` reported exactly those two available with nothing refused —
  a real binding, and still not a sandbox. The project that measured it
  recorded the limit as mattering more than the result, which is the right
  ranking.
- **Detect:** an instantiated agent, or a project's own measurement file,
  describes a `tools:` list as what makes an agent read-only, or names an
  agent holding `Bash` as unable to modify anything.
- **Remedy:** state the limit where the binding is claimed. Nothing needs
  rewiring: the reviewers' discipline was always prose, and this makes the
  file say so. Where a project genuinely needs a mechanically read-only
  agent, that is a `tools: Read` agent plus a decision about how it gets its
  diff — the operator's call, not a silent edit.
